# 会议资料整理服务 · 技术方案

> 版本 v1.0（2026-11-21）｜目标读者：你的运维/开发 ｜ 部署目标：腾讯云 CVM（Ubuntu）＋ Docker Compose
> 一句话：**把本目录已经验证过的"解析 → 编排 → 渲染 → 自检"流程做成一个单人可用的 Web 服务，解析与版式全部复用现有零依赖脚本（确定性），只有"理解材料、写纪要"交给 DeepSeek API。**

## 一、结论先行

| 项 | 结论 |
|---|---|
| 部署形态 | 单台腾讯云 Ubuntu + Docker Compose，1 个应用容器 + 1 个 Caddy 反代容器 |
| 建议规格 | 4 核 8G / 80G SSD（PaddleOCR 是 CPU 大户，2 核会明显卡） |
| 对外暴露 | 公网 IP + **自签证书 HTTPS**，端口 **8081**（Caddy `tls internal`）；防火墙由你自己开，应用端口不对公网 |
| 功能范围 | **单页单任务**，不做历史任务列表；页数只做估算，不装 LibreOffice |

| 模型 | DeepSeek API `deepseek-chat`（默认）/ `deepseek-reasoner`（可选），token 走服务端环境变量 |
| 渲染 | **直接复用本仓库 `tools/`**（`md2docx.py`、`verify_docx.py`、`docx2md.py`、`outline_docx.py`），保证版式与 SOP 逐项一致 |
| 图片 | 本地 PaddleOCR（CPU），长截图按 2100px 切片，**内容不出服务器** |
| 输出 | `02_会议纪要.md` + `03_<主标题>.docx`（A4 / 页脚页码 / 表 N 编号 / 章号连续） |

| 任务上限 | 单文件 50MB，单任务 20 分钟，并发 2 |
| 单次成本 | 约 2—4 万输入 token + 6—10k 输出 token，按 DeepSeek 官网价折算量级在 **几分钱/次**（OCR 本地，无额外成本） |
| 交付周期 | 5 个里程碑，约 12—16 人日（含部署上线） |

```
   浏览器 ══ HTTPS ══▶  │  Caddy :443  ──反代──▶  app :8000 (FastAPI, 非 root)                                    │
   (SSE 长连接)          │                          │                                                        │
                        │                          ├─ /auth      口令登录 + 签名 cookie                              │
                        │                          ├─ /api/tasks 上传 → 入队                                        │
                        │                          ├─ /api/tasks/{id}/events  SSE 阶段事件流                       │
                        │                          └─ /files      成品下载（带过期时间校验）                        │
                        │                          │                                                        │
                        │             ┌────────────┴─────────────┐                                          │
                        │             ▼                          ▼                                          │
                        │      解析层（确定性）              编排层（LLM）        校验层（确定性）              │
                        │   docx2md / 编码探测 / OCR     章节树 → 分节写 → 组装     identical / verify / 守恒   │
                        │             │                          │                     │                    │
                        │             └────────────┬─────────────┴─────────────────────┘                    │
                        │                          ▼                                                        │
                        │             渲染层：复用 tools/md2docx.py → docx                              │
                        │             存储：/data/tasks/{task_id}/   SQLite: /data/app.db                │
                        └───────────────────────────────────────────────────────────────────────────────┘
                                                    │
                                            DeepSeek API（仅文本，token 在 env）
```

**核心分层原则**：能确定性做的，绝不给模型做。

| 层 | 谁来做 | 为什么 |
|---|---|---|
| 文件解析（docx→md、编码识别、OCR、图片切片） | 本地脚本 / PaddleOCR | 可复现、零 token、可自证 |
| 理解与写作（章节树、要点、决策、待办） | DeepSeek API | 只有这一层真的需要语言模型 |
| 渲染与版式（A4、页码、表 N、字号层级） | `tools/md2docx.py` | 与 SOP 完全同源，不重写 |
| 自检（identical / verify / 章号连续 / 数字守恒） | 本地脚本 + 规则 | 模型不能自己给自己打分 |

## 四、关键设计决策

### D1 渲染层直接吃本仓库的 `tools/`，不重写

SOP 的版式（A4 11906×16838、内容宽 9026、页脚 `— 页码 —`、表 N＋表题、黑体/宋体字号层级、章号「一、／（一）／1.」）已经固化在 `md2docx.py` 里，并带 `verify_docx.py` 结构自检。**服务端以"库"的方式调用它**：

```python
# app/render.py
import sys, pathlib
TOOLS = pathlib.Path(__file__).parent / "tools"      # 镜像内 /app/tools
sys.path.insert(0, str(TOOLS))
import md2docx, verify_docx, outline_docx, docx2md   # 零依赖，只用 stdlib
```

- 好处 1：**改版式只改一处**（`tools/md2docx.py`），服务与本地手工整理完全同步。
- 好处 2：`verify_docx.py` 的子元素顺序检查（pPr/rPr/tcPr/trPr）继续生效，Word 打不开的风险维持在当前的低位。
- 约束：镜像里必须钉住 `tools/` 的版本（`tools/VERSION` 文件 + 启动时打印哈希），避免"线上版式"漂移。

### D2 解析全确定性：docx 走 identical，txt 走严格解码，图片走双遍 OCR

| 输入 | 解析方式 | 可自证性 |
|---|---|---|
| `.docx` | `docx2md.convert()` + `docx2md.verify()` | **强**：`identical（N 字符）`，与 SOP 完全一致 |
| `.txt/.md` | 编码探测（UTF-8 / UTF-8-BOM / UTF-16LE/BE / GB18030）→ 严格解码 → 乱码率判定 | **中**：解码成功 + 乱码率 < 0.5% |
| `png/jpg` | 切片 → PaddleOCR（两套参数各跑一遍）→ 两遍逐行比对 | **中**：一致率 ≥ 99.5%，否则人工确认 |

**乱码判定规则（对应你的"解析不出来要报错"）**：

```python
def decode_strict(raw: bytes) -> tuple[str, str]:
    """返回 (文本, 编码)。全部候选都失败或乱码率超阈值则抛 ParseError。"""
    for enc in ("utf-8-sig", "utf-8", "utf-16", "gb18030"):
        try:
            text = raw.decode(enc)          # 严格模式，不传 errors 参数
        except UnicodeDecodeError:
            continue
        if _garbage_ratio(text) < 0.005:    # 见下
            return text, enc
    raise ParseError("无法识别文件编码或解码后乱码过多（已尝试 utf-8/utf-16/gb18030）")

def _garbage_ratio(text: str) -> float:
    """乱码特征：替换符、C0 控制符（除 \t\n\r）、私用区、成片的非常用符号。"""
    bad = sum(1 for ch in text
              if ch == "\ufffd" or ch in "\x00\x01\x02\x0b\x0c" or 0xE000 <= ord(ch) <= 0xF8FF)
    return bad / max(1, len(text))
```

> 关键：**绝不用 `errors="ignore"` 或 `errors="replace"`**。那才是"乱码也能出稿"的根源。

### D3 LLM 只写正文，不碰版式、不碰数字口径

模型输出的是**受约束的 md 片段 + JSON**，不是 docx：

- 章节树阶段：输出 JSON（章节标题、每节要点索引、对应表格设计）。
- 写正文阶段：按节输出 markdown 片段，**只允许** `##`/`###`/`####`、`- `、表格，禁止 HTML、禁止自造表号。
- 组装阶段：服务端按 SOP 模板拼装，表号由服务端按出现顺序编号（避免模型跳号）。

温度 0.2；`response_format={"type":"json_object"}` 用于结构阶段；正文阶段用纯文本 + 事后 schema 校验。

### D4 数字与专名守恒校验（防幻觉的硬闸门）

模型最容易犯的错是把"41 分"写成"45 分"、把"7 人满分"写成"6 人"。服务端做**规则校验**：

```
原件数字集合（含时段、分数、人数、金额、比例、日期）
        ∪
纪要中出现的数字集合
        ↓
差集 = 出现在纪要但原件没有的数字 → 直接判失败（除非在"疑误/待核实"章节且标注为转写疑点）
```

另外对"专名"（人名、单位、型号）做同样比对；不在原件中的专名同样进疑误清单或失败。

### D5 阶段化流水线 + 状态落盘（可观测、可续跑）

每个任务在 `/data/tasks/{task_id}/state.json` 记录阶段与产物，SSE 的每一步都对应一个真实阶段：

| 阶段 | 名称 | 产出 | 是否可跳过 |
|---|---|---|---|
| P0 | 接收与校验 | 原件落盘、MIME/魔数校验 | 否 |
| P1 | 解析 | 逐字稿 md（内部） | 否 |
| P2 | 材料画像 | 标题数/表数/字数/时间轴 | 否 |
| P3 | 结构设计 | `plan.json`（章节树＋表格设计） | 20 分钟内可复用 |
| P4 | 写正文 | `draft/*.md`（分节） | 单节可重试 |
| P5 | 组装 | `02_会议纪要.md` | 否 |
| P6 | 守恒校验 | `check.json` | 否 |
| P7 | 渲染 | `03_<主标题>.docx` | 否 |
| P8 | 结构自检 | `verify.log` / `outline.log` | 否 |
| P9 | 打包交付 | `result.zip`（md + docx） | 否 |
| P10 | 归档清理 | 删原件，成品计时 1 小时 | 否 |

任一步失败：任务置 `failed`，SSE 推 `error` 事件带**阶段名 + 人类可读原因 + 是否可重试**，前端给"从失败阶段重试"按钮（P3 之后重试不重新解析）。

### D6 单容器 + SQLite，不引入 Redis/Celery

并发只有 2，任务表几十行，用 `asyncio.Queue` + SQLite 足够：

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,            -- uuid4
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  status TEXT NOT NULL,           -- queued|running|failed|done|expired
  stage TEXT,                     -- P0..P10
  filename TEXT, filesize INTEGER, ext TEXT,
  title TEXT,                     -- 主标题（模型抽取/用户可改）
  error TEXT, retryable INTEGER DEFAULT 0,
  result_path TEXT, expires_at INTEGER
);
CREATE INDEX idx_status ON tasks(status, created_at);
```

> 什么时候才需要 Redis：并发 ≥ 10 或需要多副本水平扩展。当前明确不做。

### D7 SSE 事件协议（前端展示的全部依据）

```
event: stage
data: {"seq":3,"task":"8f3c…","stage":"P1","name":"解析输入","state":"running","ts":1763700000.1,"elapsed":0}

event: step
data: {"seq":4,"stage":"P1","label":"docx → md 逐字转写","detail":"一致性校验: 通过 identical（9949 字符）"}

event: metric
data: {"seq":5,"stage":"P2","k":"headings","v":40}

event: stage
data: {"seq":6,"stage":"P1","name":"解析输入","state":"done","elapsed":2.31}

event: done
data: {"seq":42,"task":"8f3c…","files":[{"name":"02_会议纪要.md","url":"/files/…/02_会议纪要.md"},
      {"name":"03_定制小型化智能控制模块及合作分工.docx","url":"/files/…/03_….docx"}],
      "expires_at":1763703600}
```

- `id:` 用 `seq`，浏览器断线后带 `Last-Event-ID` 自动续传（服务端回放已发生事件）。
- 心跳：每 15 秒 `: ping`，避免 Caddy/NAT 掐断长连接。
- 一定时间（20 分钟）无事件即断开并提示超时。

## 五、输入解析层

### 5.1 文件准入（先拒绝，再解析）

| 检查 | 规则 | 不通过 |
|---|---|---|
| 大小 | ≤ 50 MB | `413 FILE_TOO_LARGE` |
| 扩展名 | `.docx/.txt/.md/.png/.jpg/.jpeg` | `415 UNSUPPORTED_TYPE` |
| 魔数 | docx=`PK\x03\x04`；png/jpg 按标准头；txt/md 跳过 | `415 TYPE_MISMATCH`（防改扩展名） |
| docx 解压上限 | 解压后总大小 ≤ 200MB、条目 ≤ 2000（防 zip bomb） | `413 ZIP_BOMB_SUSPECT` |
| 文件名 | 仅保留 basename，剥离 `..`、`/`、控制符 | 自动净化 |

### 5.2 docx：走既有 identical 链路

```python
md_text, doc = docx2md.convert(path, keep_symbols=False, auto_map=False, report=False)
ok, msg = docx2md.verify(doc, md_text)          # identical（9949 字符）/ 首个差异定位
if not ok:
    raise ParseError(f"docx 转写不一致，可能是加密文档或含不受支持的域：{msg}")
```

> 已实测覆盖 Word 直接格式、自动编号、outline 偏移等情况；261118（7489 字符）、261119（9949 字符）均为 identical。

### 5.3 图片：切片 + 双遍 OCR

```python
from PIL import Image
Image.MAX_IMAGE_PIXELS = None                   # 18428px 长图必须放开默认上限

def slice_image(src: Path, out_dir: Path, chunk=2100, overlap=120):
    img = Image.open(src)
    w, h = img.size
    y, i = 0, 1
    while y < h:
        box = (0, y, w, min(y + chunk, h))
        img.crop(box).save(out_dir / f"part{i:02d}.png")
        y += chunk - overlap                         # 重叠 120px，防止切断文字
        i += 1
```

- OCR 引擎适配层 `app/parse/ocr_engine.py`（吸收 2.x / 3.x 的 API 差异，本机 3.13 与镜像 3.11 同一套调用）：

```python
# app/parse/ocr_engine.py
def make_ocr():
    from paddleocr import PaddleOCR
    try:                                  # 3.x
        return PaddleOCR(use_doc_orientation_classify=False,
                         use_doc_unwarping=False,
                         use_textline_orientation=True, lang="ch"), "3"
    except TypeError:                     # 2.x
        return PaddleOCR(use_angle_cls=True, lang="ch"), "2"


def ocr_lines(engine, version, image_path):
    """统一返回 [(文本, 置信度, 左上y, 左上x)]，按 y 再按 x 排序。"""
    if version == "3":
        res = engine.predict(str(image_path))
        lines = []
        for page in res:
            texts = page["rec_texts"]; scores = page["rec_scores"]; boxes = page["rec_boxes"]
            for t, s, b in zip(texts, scores, boxes):
                lines.append((t, float(s), int(b[1]), int(b[0])))
    else:
        res = engine.ocr(str(image_path), cls=True)[0] or []
        lines = [(t, float(s), int(box[0][1]), int(box[0][0])) for box, (t, s) in res]
    return sorted(lines, key=lambda x: (x[2], x[3]))
```

- **模型缓存与预热（重要）**：paddleocr 3.x 首次运行会去 modelscope/bcebos 下载检测+识别模型（实测 `PP-OCRv6_medium_det` 的 `inference.pdiparams` 就有 **62MB**）。服务若在首个请求时才下载，必然撞上 20 分钟超时。因此：
  - 缓存目录固定：`PADDLE_PDX_CACHE_HOME=/opt/models`（镜像内），并把该目录 `chown` 给运行用户；
  - **镜像构建时预热**（见 §12.2 的 Dockerfile），把模型打进镜像层；
  - 服务器需能出网访问 `modelscope.cn` 与 `*.bcebos.com`；如果出网受限，改成在构建机上下载好模型目录再 `COPY` 进镜像。
- **双遍校验**：第二遍用不同 `det_db_unclip_ratio` 再跑，两遍逐行比对；一致率 < 99.5% 时把差异段落标黄交给用户确认（前端展示"待确认片段"）。
- 长图上限：单边 ≤ 30000px（超过则先等比缩到 30000 再切）。

### 5.4 解析失败的报错文案（给用户看的话术）

| 场景 | 文案 |
|---|---|
| 编码认不出 | 文件编码无法识别（已尝试 UTF-8 / UTF-16 / GB18030），请另存为 UTF-8 后重试 |
| 解码成功但乱码多 | 解码后乱码率 3.2%（阈值 0.5%），疑似文件损坏或非文本内容，请检查原文件 |
| docx 加密 | 文档受密码保护，无法读取，请先另存无密码版本 |
| docx 转写不一致 | 逐字转写校验未通过（首个差异在第 N 字符），为防改动原文已中止，请联系管理员 |
| 图片无文字 | 识别到 0 行有效文字，可能不是文字截图 |
| OCR 依赖未安装 | 服务启动时按需导入；图片任务返回 `501 OCR_UNAVAILABLE`："图片识别组件未安装（paddleocr），本次仅支持 docx/txt" |

## 六、生成编排层

### 6.1 阶段与模型调用

| 阶段 | 输入 | 模型调用 | 输出 |
|---|---|---|---|
| P3 结构设计 | 逐字稿全文（截断至 24k 字）+ 材料画像 | 1 次（JSON） | `plan.json`：章节树、每节要点索引、表格设计（列名/来源） |
| P4 写正文 | 每节对应原文片段（按要点索引回取，每节 ≤ 6k 字） | N 次（节数，串行或 2 并发） | 每节 md 片段 |
| P5 组装 | 各节片段 + plan | 0 次（服务端模板） | `02_会议纪要.md` |

> **为什么分节写**：2 小时会议逐字稿约 1—2 万字，一次生成容易"后段糊"；分节后可对每节单独重试，SSE 也能做到"第 3/7 节完成"这类细粒度进度。

### 6.2 提示词骨架（P3 结构设计，要求 JSON）

```text
你是会议纪要的结构设计师。下面是一份会议逐字稿（来源：{来源类型}），
请按《会议资料整理SOP》设计交付稿的章节树，不要写正文。

硬约束：
1) 章节用「一、／（一）／1.」三级，最多 3 级，章号从「一」连续，不得跳号。
2) 保留原文的议题时间区间，形如 13:51—14:05。
3) 表格 3—6 张，必须包含：议题速览、共识/决策汇总、待办与分工；列名自拟但要能落地。
4) 每节给出 evidence：该节依据的原文片段起止标记（用原文中出现过的唯一短句），
   便于服务端回取原文，避免你编造内容。
5) 只输出 JSON，符合给定 schema。

schema（节选）：
{"title":"主标题","subtitle":"副标题","sections":[
  {"no":"一","heading":"会议概况","children":[
     {"no":"（一）","heading":"基本信息","points":["…"],"evidence":["原文唯一短句"]}]}],
 "tables":[{"no":1,"caption":"议题速览","columns":["序号","议题","时间区间","核心内容"]}]}
```

### 6.3 写正文的硬约束（写进 system prompt）

- 只用 `##/###/####`、`- `、`|表格|`；不写 `<div>`、不写 emoji 标题、不自己编号表。
- **数字、金额、时间、型号一律照抄原文**；同一事实多个口径并列写，不许自行取舍。
- 决策分「已确认／待确认／建议」三类；"建议"必须显式标注是提炼而非原文。
- 原文里的转写疑点（人名、术语）进「疑误清单」，不在正文里擅自改正。
- 不写"综上所述""总而言之"；正文一段 2—5 行。

### 6.4 重试与降级

| 情况 | 处置 |
|---|---|
| HTTP 429 / 5xx | 指数退避重试 3 次（1s/4s/16s），仍失败置任务 `failed(retryable=true)` |
| 单次调用 > 90s | 断开重试；正文阶段可把该节再切两半 |
| JSON 解析失败 | 用"只输出 JSON"重试 1 次；再失败则退回"文本大纲 → 服务端解析"，仍失败才报错 |
| 余额不足 / key 失效 | 立即失败并给出明确文案（不要重试烧时间） |
| 20 分钟总超时 | 终止任务，保留已完成阶段产物，允许从 P3/P4 续跑 |

## 七、校验层（对应 SOP §10 验收清单）

服务端在渲染前后各跑一遍，结果全部进 SSE：

| 检查 | 实现 | 不通过 |
|---|---|---|
| 逐字稿保真 | `docx2md.verify` → identical（docx 输入）；图片走双遍 OCR 一致率 | 失败即中止 |
| md 与 docx 一致 | `verify_docx.py` 退出码 0 | 失败即中止 |
| 结构完整 | `outline_docx.py`：标题数、层级 | 记录，不中止 |
| **章号连续** | 正则抽 `一、二、三…`，检查等差不跳号 | 中止并要求重排 |
| 表号与表题 | `表 N　` 连续、每表有题 | 服务端重编，不中止 |
| 表格列宽 | 解析 `tblGrid` 总和 == 9026、最窄 ≥ 810 | 中止（版式会坏） |
| **数字/专名守恒** | D4 规则 | 中止或降级为"疑误清单" |
| 页数 | 按"行数×行高 / 版心高度"粗估 | 仅展示"约 N 页"，不做精确校验 |

> 页数：你已确认**不需要精确页数**，因此**不装 LibreOffice**（省 400MB 镜像），只给"约 N 页"的估算，用于判断内容量是否异常（< 3 页或 > 25 页会提示）。

## 十、认证与安全

### 10.1 登录（好输入 + 一次登录长期免登）

**已选：A 共享口令**。下表 B 仅作扩展位保留（代码里两种模式都实现，切换只改 `.env` 一行）。

| 模式 | 配置 | 优点 | 缺点 |
|---|---|---|---|
| **A 共享口令**（✅ 已选） | `AUTH_PASSWORDS=huiyi2026` | 零维护，1 行配置 | 不知道是谁在用；泄露后只能整体改口令，全员下线 |
| B 每人独立口令（扩展位，暂不启用） | `AUTH_USERS=zhangsan:zs1234,lisi:ls5678` | 日志可追到人；可单独停用某人；可单独设过期 | 要维护一份名单；多约 0.5 人日 |

两种模式共用的机制：

- 口令只存 **argon2/bcrypt 哈希**（`AUTH_*` 里写明文仅为方便你改，服务启动时转哈希进内存），明文不落盘、不进日志。
- Cookie：`session=<HMAC(用户标识|到期时间, SECRET)>`，`HttpOnly; Secure; SameSite=Lax; Max-Age=2592000`（30 天）。换 `SECRET` 即全员下线。
- 同设备免登：不做 device 指纹（易误伤），直接用 30 天 cookie；前端"记住我"不可关闭。
- 失败保护：同 IP 连续 5 次失败 → 锁 10 分钟（内存计数，重启清零）。
- 模式 B 额外：日志与页面页脚显示"当前用户：张三"；`/auth/logout` 只清自己的 cookie。

### 10.2 传输与暴露

- **形态**：公网 IP + **自签证书 HTTPS**，监听 **8081**。Caddy 用 `tls internal` 生成内部 CA 签发的证书，浏览器首访会警告"不安全"，点"高级→继续前往"即可（你已确认接受）。
- **为什么坚持 HTTPS 而不是裸 HTTP**：登录口令和 cookie 会随请求走公网。裸 HTTP 等于把口令明文发到互联网上；自签虽然有警告，但链路是加密的。
- **端口**：只开放 8081（TCP），由你在腾讯云安全组/防火墙放行；应用容器内部的 8000 不映射到宿主机。
- **证书有效期**：`tls internal` 默认 12 小时轮换，重启容器后浏览器可能再警告一次，属正常。若以后想免警告，申请个域名换 Let's Encrypt 即可，代码与配置都不用改。
- **口令即门禁**：既然公网可达，口令长度建议 ≥ 10 位混合字符；你也已确认"只告诉指定人"，请不要再把 URL 发到群里。
- **可选加固**：在 Caddyfile 里加一层 IP 允许列表（`@blocked not remote_ip ...`），只放行你和指定人的常用出口 IP；代价是对方换网络就进不来。

### 10.3 容器与运行

- 非 root 用户（uid 10001）运行；`read_only: true` + `tmpfs /tmp` + 只挂 `/data`。
- 上传文件仅存 `/data`，且路径由服务端生成（用户文件名只用于展示与下载名）。
- 禁止任何"按文件名拼路径"的逻辑（防路径穿越）。
- 日志：JSON 结构化，字段白名单；**`DEEPSEEK_API_KEY`/cookie/正文内容不进日志**（只记长度与哈希前 8 位）。

### 10.4 隐私（家长会这类材料含真实姓名）

- 图片 OCR 全本地，不调用第三方视觉接口。
- 原件任务结束即删；成品 1 小时清；`work/` 同步删。
- 管理端点 `/admin/tasks`（可选）：只显示文件名与状态，不显示正文摘要。

`Caddyfile`（自签，无域名）：

```caddyfile
# 把 203.0.113.10 换成你的公网 IP；Caddy 用它作为证书的 IP SAN
https://203.0.113.10:8081 {
    tls internal                    # 内部 CA 自签，浏览器会警告，接受即可

        flush_interval -1           # SSE 必须关缓冲，否则进度会"最后一秒全出来"

    }
    request_body {
        max_size 60MB
    }
}
```

> **硬约束**：`paddlepaddle 2.6.*` 只发布到 **cp312**，Python 3.13 上装必然报
> `Could not find a version that satisfies the requirement paddlepaddle==2.6.*`。
> 两个版本线的 **PaddleOCR API 不同**（2.x：`ocr.ocr(img, cls=True)`；3.x：`ocr.predict(img)` + `rec_texts`），
> 因此服务端用 `app/parse/ocr_engine.py` 做适配（见 §5.3），本机与线上行为一致。

仓库里的依赖文件（按用途拆开，避免装错线）：

| 文件 | 内容 | 用途 |
|---|---|---|
| `requirements-core.txt` | FastAPI/uvicorn/httpx/Pillow/argon2 等 | 通用；不装 OCR 也能跑通 docx/txt 全链路 |
| `requirements-ocr-py313.txt` | `paddlepaddle==3.3.1` + `paddleocr>=3.0` | 本机 Python 3.13 |
| `requirements-ocr-py311.txt` | `paddlepaddle==2.6.2` + `paddleocr==2.9.1` | 服务器 Python 3.10/3.11 |
| `requirements.txt` | core + py313 | 本机一键 |
| `requirements-server.txt` | core + py311 | 镜像一键（Dockerfile 用这个） |

**Windows + Python 3.13 的最短可用路径**（先跑通流程，OCR 可以后装）：


**常踩的坑**：

| 现象 | 原因 | 处理 |
|---|---|---|
| `pip install paddlepaddle` 卡住/超时 | 包约 500MB，走海外源慢 | 已配阿里云镜像；仍慢可加 `--timeout 120` |
| **`paddlepaddle==2.6.*` 报"找不到匹配版本"** | 2.6 只发布到 cp312，**Python 3.13 没有轮子** | 3.13 改装 `paddlepaddle==3.3.1`＋`paddleocr>=3.0`（即 `requirements-ocr-py313.txt`） |
| 换 Python 版本后 OCR 报 `AttributeError: 'PaddleOCR' object has no attribute 'ocr'` | 3.x 改成了 `predict()` | 用 §5.3 的 `ocr_engine.py` 适配层，别直接调 `ocr.ocr` |
| `ImportError: libGL.so.1` | paddleocr 依赖 OpenCV 运行库 | `sudo apt install -y libgl1 libglib2.0-0`（Windows 无此项） |
| 中文显示成方框（导 PDF 时） | 缺中文字体 | `sudo apt install -y fonts-noto-cjk` |
| `python3 -m venv` 报 ensurepip 缺失 | 未装 `python3-venv` | `sudo apt install -y python3-venv` |
| OCR 首次运行慢（几十秒） | 首次自动下载检测/识别/方向模型 | 预热一次：`paddleocr --image_dir 任一图片`，模型会缓存到 `~/.paddleocr` |

## 十四、失败模式与处置

| 现象 | 根因 | 处置 |
|---|---|---|
| 进度条不动，最后一秒全出来 | 反代缓冲 SSE | Caddy `flush_interval -1`；Nginx 则 `proxy_buffering off` |
| 长连接 60 秒断 | 反代/安全组空闲超时 | 15 秒心跳 + `proxy_read_timeout 3600s` |
| 图片识别成一片乱码 | 长图被切成半行 | 校验切片边界是否落在行间（重叠 120px），必要时按 1800/2400 两档重试 |
| 纪要里出现原文没有的分数 | 模型幻觉 | D4 守恒校验拦下，任务失败并给差异清单 |
| Word 打不开产物 | OOXML 顺序错 | `verify_docx` 已覆盖；失败则拒绝交付并记录 XML 差分 |
| 模型 429 | token 限流 | 退避重试；并发降到 1 |
| 任务卡死 20 分钟 | 单节生成超长 | 该节二分再试；仍失败则整任务 failed，允许从 P4 续跑 |
| 成品下载 404 | 过期清理 | 文案说明保留 1 小时 |

## 十六、风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| 模型改动 SOP 版式 | 交付稿格式不一致 | **版式由代码生成，模型只写正文**；组装用固定模板 |
| 模型幻觉数字/人名 | 事实错误 | 守恒校验 + 疑误清单 + 前端"待确认片段" |

| 镜像 1.5GB，冷启动慢 | 首次部署久 | 多阶段构建 + 分层缓存；必要时 OCR 拆 sidecar |
| 单机单容器 | 进程挂了服务中断 | `restart: unless-stopped` + healthcheck + 每日 DB 备份 |
| 家庭网络/手机端 SSE 不稳 | 进度看不到 | 断线用 `Last-Event-ID` 续传，兜底 `/api/tasks/{id}` 轮询 |

### 17.2 与 SOP 的逐项对齐（验收表）

| SOP 要求 | 服务端如何保证 |
|---|---|
| md 是唯一真源，docx 只是渲染物 | 只从 `02_会议纪要.md` 渲染 docx，不直接改 docx |
| 逐字稿必须机器自证 | docx：`identical`；图片：双遍 OCR 一致率 ≥ 99.5% |
| 交付稿必须 verify 0 退出 | P8 强制跑 `verify_docx.py`，非 0 不交付 |
| 需要页码 | `md2docx` report 主题自带 PAGE 域 |
| A4 / 边距 / 字号层级 | 由 `md2docx.THEMES["report"]` 决定，模型无法改 |
| 表 N＋表题、列宽总和 9026 | 服务端编号 + `alloc_widths()` 保证 |
| 章号连续 | `guard.py` 正则校验，不连续即失败 |
| 质疑清单 / 疑误清单 | 强制章节，模型必须填；守恒校验的差集也进这里 |
| 中间产物交付前清理 | 1 小时 TTL |
